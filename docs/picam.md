# picam.py — Pi 카메라 캡처와 멈춤 자동 복구

## 역할

라즈베리파이 카메라(Camera Module v2, IMX219 센서)에서 프레임을 계속 받아 **가장 최근 한 장**을 보관한다. 실시간 화면(`mjpeg.py`), 움직임 감지(`motion.py`), 화면 저장이 이 한 장을 가져다 쓴다. 녹화(`recorder.py`)는 같은 카메라의 하드웨어 H.264 인코더를 쓴다.

추가로 두 가지를 한다.
- 모든 프레임 왼쪽 위에 날짜/시각을 그려 넣는다.
- 카메라 센서가 멈추면(가끔 생기는 하드웨어 문제) 감지해서 재부팅 없이 복구한다.

## 코드 구조

| 이름 | 하는 일 |
|---|---|
| `SENSOR_MODE` 등 상수 | 센서 모드, 시각 표시 위치·글꼴, 멈춤 감시 시간 |
| `draw_timestamp(request)` | 카메라가 프레임을 만든 직후 날짜/시각을 그림 (`pre_callback`) |
| `run_with_timeout(fn, timeout)` | 함수를 별도 스레드에서 실행하고 시간 안에 안 끝나면 `TimeoutError` |
| `CameraEventLog` | 멈춤/복구 기록을 `logs/camera_events.log`(JSON 한 줄씩)에 남기고, 최근 24시간 기록을 돌려줌 |
| `VideoGet` | 카메라 열기, 캡처 스레드, 최신 프레임 보관, 멈춤 감지·복구 |

`VideoGet`의 주요 멤버:
- `frame` (속성): 최신 프레임의 복사본. 여러 스레드가 동시에 읽으므로 `Lock`으로 보호하고 복사해서 준다.
- `picam2`: 현재 열려 있는 `Picamera2` 객체. 복구할 때 새 객체로 바뀐다.
- `camera_lock`: 카메라를 다시 여는 동안 녹화가 카메라를 건드리지 못하게 막는 잠금.
- `before_restart` / `after_restart`: 다시 열기 전후에 부를 함수 목록. `PiRecorder`가 여기에 "녹화 멈춤/재개"를 등록한다.
- `on_fatal`: 복구가 안 될 때 부를 함수. `app.py`가 "녹화 닫고 프로세스 종료"를 넣는다.
- `status()`: 웹 배너용 상태 (지금 멈췄는지, 마지막 프레임 시각, 최근 24시간 기록).

## 사용 라이브러리와 선택 이유

| 라이브러리 | 용도 | 선택 이유 |
|---|---|---|
| **Picamera2** | 카메라 제어, 프레임 캡처, 하드웨어 인코더 | 라즈베리파이 공식 카메라 라이브러리(libcamera 기반). OpenCV `VideoCapture`로는 최신 Raspberry Pi OS의 CSI 카메라를 직접 열 수 없다 |
| **OpenCV (`cv2`)** | 시각 글씨 그리기 | 이미 프로젝트 전체에서 이미지 처리에 쓰고 있음 |
| `threading` | 캡처 전용 스레드, 잠금 | 웹 요청과 상관없이 프레임을 계속 받아야 함 |

## 동작 원리

### 1. 왜 별도 스레드로 계속 받아두나

카메라는 초당 수십 장을 만든다. 웹 요청이 올 때마다 카메라에 "한 장 줘"라고 하면 요청마다 기다려야 하고, 여러 사람이 보면 서로 경쟁한다. 그래서 캡처 스레드 하나가 계속 받아 **최신 한 장만** 덮어써 두고, 필요한 쪽은 그 한 장을 복사해 간다.

### 2. 센서 모드와 화각

카메라 센서(IMX219)는 3280x2464 픽셀이고, 읽는 방식(센서 모드)이 여러 개다.

| 센서 모드 | 읽는 방식 | 화각 (가로 × 세로) |
|---|---|---|
| 3280x2464 | 전체를 그대로 | 62° × 49° (느림) |
| **1640x1232** | 전체를 2x2씩 묶어서 (binning) | 62° × 49° |
| 1920x1080 | **가운데만 잘라서** | 39° × 22.5° |

화각은 렌즈 초점거리(3.04mm)와 센서에서 실제로 쓰는 폭으로 계산한다. 픽셀 하나가 1.12μm이므로:

```
가로 화각 = 2 × atan( (사용 픽셀 수 × 1.12μm / 2) / 3.04mm )
1920픽셀: 2 × atan(1.075 / 3.04) ≈ 38.9°
3280픽셀: 2 × atan(1.837 / 3.04) ≈ 62.3°
```

출력을 1280x720(16:9)으로만 정하면 libcamera가 비율이 같은 1920x1080 모드를 고르는데, 이게 가운데만 잘라 쓰는 모드라 화면이 좁았다. 그래서 `SENSOR_MODE = (1640, 1232)`로 지정한다. 1640x1232는 4:3이라, 16:9로 출력할 때 ISP가 위아래만 잘라서 **가로 62.3° × 세로 37.5°**가 된다(`ScalerCrop` 3280x1844로 확인). 속도는 두 모드 모두 34fps로 같았다.

### 3. 날짜/시각 그리기 (`pre_callback`)

Picamera2의 `pre_callback`은 프레임이 만들어진 직후, 앱이나 인코더에 전달되기 **전에** 불린다. 여기서 `MappedArray`로 프레임 메모리에 직접 글씨를 쓰면 실시간 화면, 녹화(H.264), 화면 저장, 움직임 감지가 모두 같은 글씨가 찍힌 프레임을 받는다. 밝은 배경에서도 보이도록 검은 굵은 글씨(두께 6) 위에 흰 글씨(두께 2)를 겹쳐 그린다.

매초 바뀌는 초 숫자가 움직임 감지에 걸리지 않는지 확인했다: 글씨 영역의 변화량은 최대 0.043%로 감지 기준(0.5%)보다 훨씬 작다. 감지할 때 320x180으로 줄이고 흐리게 해서 숫자 변화가 거의 지워진다.

### 4. 멈춤 감지

센서가 프레임을 안 보내면 libcamera는 `Camera frontend has timed out!`을 남기고 스스로 복구하지 않는다. 예전 코드는 `capture_array()`를 **시간 제한 없이** 불러서 영원히 기다렸다.

지금은 이렇게 기다린다.

```python
job = self.picam2.capture_array(wait=False)          # "다음 프레임 줘" 요청만 하고 바로 돌아옴
new_frame = self.picam2.wait(job, timeout=5)          # 5초까지만 기다림, 넘으면 TimeoutError
```

`TimeoutError`(또는 다른 카메라 오류)가 나면 `_recover()`로 간다.

### 5. 복구 단계

```
프레임이 5초 넘게 안 옴
  → 멈춤 기록 시작 (시작 시각 = 마지막 프레임 시각)
  → [시도 1~3] run_with_timeout(_reopen, 30초)
       _reopen: 녹화 멈춤(before_restart) → stop() → close() → 1초 대기
                → 새 Picamera2 열기 → 녹화 재개(after_restart)
       · 새 카메라에서 프레임이 오면 → "복구됨" 기록
       · 열기 실패 → 5초 뒤 다시 시도
       · 30초 안에 안 끝남(닫기 자체가 멈춤) → 즉시 "실패"
  → 3번 넘게 실패 또는 닫기가 멈춤 → on_fatal() → 녹화 파일 닫고 프로세스 종료
  → systemd(Restart=always)가 5초 뒤 서비스를 새로 띄움
```

`run_with_timeout`이 필요한 이유: 시험해보니 프레임 요청이 걸려 있는 상태에서 `picam2.stop()`이나 녹화 인코더 멈추기가 **끝나지 않는** 경우가 있었다. 파이썬에는 다른 스레드를 강제로 멈추는 방법이 없으므로, 별도 스레드에서 실행하고 시간이 지나면 포기한 뒤 프로세스째 다시 시작하는 게 가장 확실하다. 서비스 재시작으로 카메라가 살아나는 것은 실제 멈춤 상황에서 확인했다.

### 6. 기록과 배너

멈춤 한 건이 끝나면(복구 또는 실패) 이런 한 줄이 `logs/camera_events.log`에 쌓인다.

```json
{"camera": "pi", "start": "…", "end": "…", "duration_s": 7.4, "attempts": 1,
 "result": "recovered", "message": "카메라를 다시 열어 자동 복구됨", "error": "TimeoutError"}
```

`/status` API가 `status()`를 돌려주고, 웹의 `static/js/status_alert.js`가 10초마다 확인해 빨간(멈춤 중)/노란(최근 24시간 복구) 배너를 띄운다.

## 설정값과 근거

| 상수 | 값 | 근거 |
|---|---|---|
| `SENSOR_MODE` | (1640, 1232) | 센서 가로 전체 사용, 화각 62°. 1920x1080은 크롭 모드 |
| 출력 | 1280x720 RGB888 | 실시간 화면, 녹화 모두 720p로 충분, CPU 부담 고려 |
| `FRAME_TIMEOUT` | 5초 | 정상 동작 중 프레임 간격(약 30ms)보다 충분히 길고, 멈춤을 빨리 알아챌 만큼 짧음 |
| `MAX_RESTART_ATTEMPTS` | 3 | 일시적 실패는 재시도, 계속되면 프로세스 재시작이 더 확실 |
| `REOPEN_TIMEOUT` | 30초 | 정상 다시 열기는 수 초면 끝남. 이보다 길면 멈춘 것으로 판단 |

## 시험 방법과 결과

진짜 센서 멈춤은 일부러 만들 수 없어서, 서비스를 멈추고 같은 코드를 띄운 뒤 "프레임이 안 오는 상황"을 흉내 냈다.

| 상황 | 흉내 낸 방법 | 결과 |
|---|---|---|
| 다시 열면 살아남 | 현재 카메라의 `wait`가 항상 `TimeoutError`를 내게 바꿈 | 7.4초 만에 복구, 녹화도 새 파일로 이어짐 |
| 다시 열기가 계속 실패 | `_open_camera`가 항상 예외를 내게 바꿈 | 3번 시도 후 27초 만에 `on_fatal` |
| 닫기 자체가 멈춤 | `stop`이 영원히 잠들게 바꿈 | 시간 제한 후 `on_fatal` |

## 한계

- 진짜 센서 멈춤에서 "다시 열기"가 통하는지는 아직 실제로 확인하지 못했다 (안 통하면 서비스 재시작으로 넘어감).
- 센서가 멈추는 하드웨어 원인은 해결하지 못했다 (`docs/troubleshooting.md` 2번).
- 녹화 쪽이 카메라를 막아도 멈춤으로 보인다. 실제로 녹화 faststart 때문에 오작동한 적이 있다 (`docs/troubleshooting.md` 1번).
