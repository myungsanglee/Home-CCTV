# webrtc_video.py — 실시간 영상 (WebRTC, H.264 그대로 전달)

## 역할

실시간 화면을 WebRTC로 보낸다. 카메라 쪽에서 **이미 압축된 H.264를 다시 압축하지 않고** 브라우저까지 그대로 전달한다.

- **Pi 카메라**: 녹화용 하드웨어 인코더(`recorder.PiRecorder`)가 만든 H.264를 녹화와 실시간 보기가 나눠 쓴다.
- **Tapo**: 카메라가 RTSP로 보내는 H.264(stream2, 720p)를 그대로 넘긴다 (`tapo.TapoLive`).

예전 방식인 MJPEG(`docs/mjpeg.md`)는 WebRTC가 안 될 때 쓰는 예비 경로로 남겨뒀다.

## 왜 바꿨나

MJPEG로 볼 때 집 Wi-Fi에서도 화면이 자주 버벅였다. 측정해 보니 영상이 너무 무거웠다 (`docs/troubleshooting.md` 16번).

| 항목 | MJPEG (JPEG 품질 95) | H.264 (지금) |
|---|---|---|
| Pi 카메라 | 한 장 약 316KB × 20fps = **52Mbps** | 약 **1.5Mbps** (녹화 인코더 설정값) |
| Tapo | 한 장 약 182KB × 20fps = **30Mbps** | 약 **0.2Mbps** (움직임 없는 장면) |

보통 영상통화는 1~3Mbps를 쓴다. MJPEG는 그보다 20배쯤 무거웠고, 버퍼가 없는 방식이라 전송 속도가 잠깐만 떨어져도 화면이 멈췄다.

### MJPEG와 H.264의 차이

- **MJPEG**: 매 장면을 사진(JPEG) 한 장으로 따로 압축한다. 화면이 거의 그대로여도 매번 사진 전체를 다시 보낸다.
- **H.264**: 가끔 화면 전체를 담은 **키프레임(I 프레임)** 을 보내고, 그 사이에는 앞 화면과 **달라진 부분만** 담은 **차이 프레임(P 프레임)** 을 보낸다. 배경이 거의 안 바뀌는 고양이 CCTV는 차이 프레임이 아주 작아서 수십 배 줄어든다.

화질은 같은 1280x720이다. Tapo는 원래 카메라가 보낸 H.264를 MJPEG로 다시 압축하던 것이라, 지금이 오히려 손실이 한 번 적다. Pi 카메라는 녹화 영상과 같은 화질이 됐고, 움직임이 많은 장면에서 조금 뭉개질 수 있다.

## 사용 라이브러리와 선택 이유

| 라이브러리 | 용도 | 선택 이유 |
|---|---|---|
| **aiortc** | 파이썬 WebRTC 서버 | 소리에 이미 쓰고 있음. 압축된 패킷을 그대로 보내는 기능(`encoder.pack`)이 공식 지원됨 |
| **PyAV** | Tapo RTSP에서 압축된 패킷 꺼내기 | 디코딩 없이 패킷만 꺼낼 수 있음(`demux`) |
| **Picamera2** 출력 목록 | 인코더 하나의 출력을 녹화와 실시간 보기로 나눔 | 인코더에 출력을 여러 개(리스트) 줄 수 있음 |

**검토한 다른 방법: MediaMTX** (전용 스트리밍 서버). 라즈베리파이 CCTV에서 많이 쓰지만, 서비스가 하나 더 늘고 로그인·탭 구조를 따로 맞춰야 한다. aiortc로 먼저 시험해서 CPU, 지연, 아이폰 재생이 모두 괜찮아서 aiortc를 택했다.

**WebRTC를 고른 이유**: 지연이 짧고(아래 측정), 브라우저가 플러그인 없이 재생하고, `<video>`에 바로 붙는다. HLS 같은 HTTP 방식은 버퍼 때문에 수 초 늦다.

## 동작 원리

### 1. 압축하지 않고 넘기기

aiortc는 영상 트랙의 `recv()`가 돌려주는 값에 따라 다르게 동작한다.

```
recv() → av.VideoFrame (압축 안 된 그림)  → aiortc가 직접 H.264/VP8로 압축 (CPU 많이 씀)
recv() → av.Packet     (이미 압축된 데이터) → 압축 없이 RTP 패킷으로 나누기만 함 (encoder.pack)
```

라즈베리파이 CPU로 720p를 소프트웨어 압축하면 연결마다 코어 하나를 다 쓴다. 그래서 `EncodedVideoTrack.recv()`는 압축된 `av.Packet`을 돌려준다. 압축은 Pi는 하드웨어 인코더가, Tapo는 카메라가 이미 했다.

### 2. 나눠 주기 (`H264Fanout`)

```
Pi 하드웨어 인코더 ─┬─▶ FfmpegAudioOutput → 녹화 파일
                    └─▶ LiveVideoOutput → H264Fanout ─┬─▶ 연결 A (EncodedVideoTrack)
                                                      └─▶ 연결 B

Tapo stream2 (RTSP) → TapoLive ─┬─ 영상 패킷 → H264Fanout ─▶ 연결들
                                └─ 소리 → AudioFanout ─▶ 소리 연결들
```

- 압축은 카메라마다 한 번이고, 보는 사람이 늘어도 나눠 주기만 한다.
- Pi: 인코더 출력이 리스트라서 녹화와 실시간 보기가 같은 H.264를 받는다. USB가 없어 녹화를 못 할 때도 실시간 보기를 위해 인코더는 돌린다.
- Tapo: 보거나 듣는 사람이 생기면(`on_first_listener`) 그때 RTSP에 연결하고, 아무도 없으면 끊는다. 영상과 소리를 한 연결로 받아서, 보면서 소리를 켜도 카메라 연결이 늘지 않는다.

### 3. 키프레임부터 시작하기

차이 프레임은 앞 화면이 있어야 그릴 수 있다. 연결 중간부터 차이 프레임을 받으면 화면이 깨진다.

- 새 연결은 **첫 키프레임이 올 때까지 프레임을 버린다.** 그래서 첫 화면이 나오는 시간 ≈ 다음 키프레임까지 남은 시간이다.
- Pi 인코더의 키프레임 간격 기본값은 60프레임(약 3.6초)이었다. `PI_KEYFRAME_INTERVAL = 30`(약 1.8초)으로 줄였다. 비트레이트는 같아서 녹화 파일 크기는 그대로다.
- Tapo는 약 2초마다 키프레임을 보낸다 (카메라 설정).
- Pi 인코더는 키프레임 앞에 SPS/PPS(해상도 등 재생 설정)를 매번 붙인다(`repeat=True`). Tapo는 혹시 빠져 있으면 RTSP 연결 정보(`extradata`)에서 붙인다 (`has_sps`).

### 4. 밀리면 버리고 다음 키프레임부터

연결마다 큐(최대 30프레임, 약 2초)가 있다. 네트워크가 느려서 큐가 가득 차면 **쌓인 것을 모두 버리고 다음 키프레임부터** 다시 보낸다. 차이 프레임을 몇 장만 빼고 보내면 다음 키프레임까지 화면이 깨지기 때문이다. 화면이 잠깐 멈추는 대신 늦은 영상이 쌓이지 않는다.

### 5. 타임스탬프

RTP 영상 시각은 90kHz 단위다. 카메라가 붙인 시각 대신 **라즈베리파이가 받은 시각**(`time.monotonic()`)으로 매긴다. Tapo가 Wi-Fi 때문에 끊겼다 다시 붙어도 시간이 거꾸로 가지 않는다.

### 6. 코덱을 H.264로 고정 (`prefer_h264`)

브라우저는 VP8, VP9, H.264 등을 제안하고, aiortc는 기본으로 VP8을 먼저 고른다. 그대로 보낼 수 있는 건 H.264뿐이라 고정한다.

**주의**: aiortc는 코덱을 **브라우저 제안(offer)을 적용하는 순간**(`setRemoteDescription`) 정한다. 그래서 트랙을 추가하고 `prefer_h264`를 부른 **다음에** offer를 적용해야 한다. 순서가 반대면 VP8이 선택되고 영상이 안 나온다 (실제로 겪음).

### 7. 프로파일

카메라 둘 다 H.264 **High 프로파일**, B 프레임 없음(I/P만)이다. aiortc는 SDP에 Baseline 프로파일만 적지만, 브라우저 디코더는 실제 데이터의 프로파일로 재생해서 아이폰 Safari, 맥북에서 모두 재생됐다. B 프레임(순서를 바꿔 보내는 프레임)이 있으면 WebRTC로 보낼 수 없는데, 두 카메라 모두 없음을 확인했다 (Tapo: 패킷 101개 중 `pts != dts` 0개).

### 8. 연결 과정

```
브라우저 (startVideo)                         서버 (/offer)
RTCPeerConnection, addTransceiver('video', recvonly)
createOffer → POST /offer {sdp, cam, media: 'video', reason} ─▶
                                               RTCPeerConnection(iceServers=[])
                                               EncodedVideoTrack 추가, prefer_h264
                                               setRemoteDescription → createAnswer
                                        ◀───── answer (라즈베리파이 주소 포함)
setRemoteDescription
영상 데이터가 들어오기 시작하면(unmute) <video>.srcObject 교체
```

- 서버는 STUN 서버를 쓰지 않는다(`iceServers=[]`). 접속이 항상 Tailscale 안에서 와서 라즈베리파이 자체 주소로 충분하다. STUN을 쓰면 연결마다 공인 주소 확인에 5초씩 걸렸다 (`docs/troubleshooting.md` 16번).
- `reason`(처음, 카메라 선택, 화면 복귀, 재연결 이유)은 서버 로그에 남겨서 화면 끊김 원인을 나중에 확인할 수 있게 한다.

### 9. 브라우저 쪽 동작 (`get_cam.html`)

- **재연결**: 연결이 `failed`면 2초 뒤 다시 연결. `disconnected`는 잠깐의 Wi-Fi 끊김이면 저절로 돌아오므로 5초 기다려 보고 다시 연결.
- **검은 화면 방지**: 다시 연결하는 동안 `<video>`를 비우지 않고 마지막 화면을 둔다. 새 연결의 영상 데이터가 실제로 들어올 때(`unmute`) 바꿔 끼운다. (처음에는 바로 비워서 다시 연결될 때마다 검은 화면이 보였다.)
- **예비 MJPEG**: 3번 연속 실패하면(첫 화면 10초 안에 안 나옴 포함) MJPEG `<img>`로 바꾼다. 주소에 `?mjpeg`를 붙이면 처음부터 MJPEG.
- **안 볼 때 끊기**: 다른 앱/탭으로 가면 연결을 끊고, 돌아오면 다시 연결한다.
- **확대/저장**: 확대·이동은 `<video>`와 `<img>`를 감싼 `#videoInner`에 `transform`을 적용해서 두 경로가 같게 동작한다. 화면 저장은 `<video>`를 캔버스에 그려서 만든다 (`videoWidth`×`videoHeight`).
- `<video>`는 `autoplay muted playsinline`. iOS는 소리 없는 영상만 자동 재생을 허용하고, `playsinline`이 없으면 전체 화면으로 열린다. 소리는 기존 소리 버튼(별도 WebRTC 연결, `docs/audio.md`)으로 듣는다.

## 설정값과 근거

| 상수 | 값 | 근거 |
|---|---|---|
| `QUEUE_FRAMES` | 30 | 약 2초. 이보다 밀리면 늦은 영상을 버리는 편이 낫다 |
| `PI_KEYFRAME_INTERVAL` (`recorder.py`) | 30프레임 | 첫 화면 대기 3.6초 → 최대 약 1.8초 |
| `FIRST_FRAME_TIMEOUT` (페이지) | 10초 | 정상이면 2초 안에 나옴 |
| `DISCONNECT_GRACE` (페이지) | 5초 | 짧은 Wi-Fi 끊김은 기다리면 돌아옴 |
| `MAX_FAILURES` (페이지) | 3번 | 계속 실패하면 MJPEG로 |

## 측정

라즈베리파이 안에서 aiortc 시험용 클라이언트로 연결해서 받은 프레임을 디코딩해 확인했다.

| 항목 | Pi 카메라 | Tapo |
|---|---|---|
| 선택된 코덱 | H264/90000 | H264/90000 |
| 받은 크기 | 1280x720 | 1280x720 |
| 프레임 수 | 초당 13~17장 | 초당 14장 |
| 연결 시간 | 0.1초 | 0.1초 |
| 첫 화면 | 0.1~1.5초 (키프레임 간격 단축 후) | 약 2초 |

- 아이폰 Safari와 맥북에서 두 카메라 모두 재생, 탭 전환, 확대, 화면 저장, 소리를 사용자가 확인했다.
- Pi 카메라 녹화는 인코더를 나눠 쓴 뒤에도 정상 (10분 파일 계속 생성, ffmpeg 종료 기록 없음).

## 한계

- 실시간 Pi 영상의 화질과 초당 장수는 녹화 설정(1.5Mbps, 약 16fps)과 같다. 더 선명하게 하려면 `PI_BITRATE`를 올려야 하고 녹화 파일도 같이 커진다.
- 패킷이 빠졌을 때 브라우저가 키프레임을 요청(PLI)해도 그대로 전달하는 구조라 들어줄 수 없다. 다음 키프레임(최대 약 2초)까지 화면이 깨지거나 멈출 수 있다.
- Tapo가 Wi-Fi로 끊기면 실시간 영상도 그동안 멈춘다 (마지막 화면 유지).
- 영상과 소리가 별도 연결이라 싱크가 조금 어긋날 수 있다.
- 실시간 보기 중에는 Tapo RTSP 연결이 하나 더 생긴다 (움직임 감지용 OpenCV, 녹화, 실시간 보기). C210에서 세 연결이 동시에 동작함을 확인했다.
