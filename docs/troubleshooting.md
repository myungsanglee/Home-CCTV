## 0. git에 남지 않는 설정

아래 설정은 저장소 밖(시스템 파일, 외부 서비스)에 있어서 코드에 남지 않는다. 라즈베리파이를 새로 설치하면 이 목록대로 다시 해야 한다. 값(IP, 계정, 주소)은 적지 않는다.

### systemd 서비스 `/etc/systemd/system/cctv.service`

```ini
[Unit]
Description=M&N Home CCTV Service
After=network.target

[Service]
User=michael
Group=michael
WorkingDirectory=/home/michael/project/Home-CCTV
ExecStart=/usr/bin/python -u /home/michael/project/Home-CCTV/app.py
Restart=always
RestartSec=5

# 종료 신호는 앱에만 보내고, 앱이 녹화 파일을 닫은 뒤 ffmpeg를 정리함 (6번 항목)
KillMode=mixed
TimeoutStopSec=60

[Install]
WantedBy=multi-user.target
```

- `Restart=always`: Pi 카메라 복구에 실패하면 앱이 스스로 종료하고(2번 항목), systemd가 5초 뒤 다시 켠다.
- 바꾼 뒤에는 `sudo systemctl daemon-reload && sudo systemctl restart cctv`.

### 녹화용 USB `/etc/fstab`

```
UUID=<USB 파티션 UUID>  /mnt/cctv  ext4  defaults,noatime,nofail,x-systemd.device-timeout=10s  0  2
```

- ext4로 포맷: exFAT/NTFS보다 정전에 강하다. Windows/macOS에서는 바로 못 읽지만 녹화는 웹에서 보고 내려받으므로 문제없다.
- `nofail`, `x-systemd.device-timeout=10s`: USB가 빠져 있어도 10초만 기다리고 부팅한다.
- 마운트 후 `sudo chown michael:michael /mnt/cctv`.
- USB는 파란색 USB 3.0 포트에 꽂는다.

### Tailscale HTTPS

1. Tailscale 관리 페이지 → DNS에서 **MagicDNS**와 **HTTPS Certificates**를 켠다.
2. 라즈베리파이에서 한 번 실행 (설정은 Tailscale에 저장돼 재부팅 후에도 유지):
   ```bash
   sudo tailscale serve --bg --https=443 http://127.0.0.1:5000
   ```
3. 접속 주소는 `https://<기기 이름>.<tailnet 이름>.ts.net`.
- 인증서를 발급하면 기기 이름이 인증서 공개 기록(CT log)에 올라간다. Tailscale 밖에서는 접속할 수 없다.

### 시스템 패키지와 OS 설정

- apt: `python3-flask python3-dotenv python3-opencv python3-numpy python3-picamera2 libportaudio2 ffmpeg exfatprogs`
  - `libportaudio2`가 없으면 `sounddevice`가 `PortAudio library not found`로 실패한다 (7번 항목).
- pip: `requirements.txt` (`--break-system-packages`)
- `raspi-config` → Interface Options → I2C 켜기 (서보 보드 PCA9685, 주소 0x40)
- `onvif-zeep`은 WSDL 파일을 `~/.local/lib/python3.4/site-packages/wsdl`에 설치한다 (경로 이름이 이상하지만 정상). 다른 곳이면 `ONVIF_WSDL_DIR` 환경 변수로 지정.

### 공유기 / 카메라

- Tapo 카메라: Tapo 앱 → 카메라 설정 → 고급 설정 → **카메라 계정** 생성 (TP-Link 클라우드 계정과 다름). 이 계정으로 RTSP/ONVIF에 접속한다.
- Tapo 카메라 IP는 공유기에서 고정한다. 바뀌면 `.env`의 `TAPO_IP`도 바꿔야 한다.
- 공유기 2.4GHz Wi-Fi(Tapo가 쓰는 대역): **채널 1, 대역폭 20MHz** (자동/40MHz일 때 Tapo가 하루 100번 넘게 끊김, 15번 항목). 라즈베리파이는 5GHz에 연결.
- 라즈베리파이 IP는 DHCP(자동)로 둬도 된다. 웹은 Tailscale 주소로만 접속하고 포트포워딩이 없어서 집 안 주소가 바뀌어도 영향이 없다.
- 예전에 열어뒀던 포트포워딩(웹, SSH, VNC, 동적 포트 범위)은 모두 닫는다. 외부 접속은 Tailscale로만 한다.
- (권장) 공유기에서 Tapo 카메라의 **인터넷만** 차단한다. RTSP/ONVIF는 집 안 네트워크 통신이라 영향이 없다. "게스트 네트워크"로 옮기면 라즈베리파이와도 통신이 막히므로 쓰지 않는다.

### `.env` 항목 (값은 저장소에 없음)

`SECRET_KEY`, `MICHAEL_PASSWORD`, `NATALIA_PASSWORD`, `TAPO_IP`, `TAPO_USER`, `TAPO_PASSWORD`

## 1. Pi 카메라가 10분마다 멈추고, 멈춤 감시가 오작동함

**증상**
- 카메라 멈춤 감시(2번 항목)를 넣은 뒤, 11월 6일~14일 사이 "Pi 카메라 멈춤" 기록이 36건 쌓였다. 매번 카메라를 다시 열어 복구했지만, 그때마다 영상과 녹화가 7~37초씩 끊겼고 짧은 녹화 파일이 생겼다.

**진단 과정**
1. `logs/camera_events.log`의 시작 시각을 보니 36건 중 **35건이 10분 정각(:00, :10, :20 …) 직후 15초 안**이었다. 녹화 파일이 바뀌는 순간이다.
2. 10분짜리 Pi 녹화 파일은 약 100MB, USB 쓰기 속도는 `dd`로 재보니 약 23MB/s였다.
3. 녹화 ffmpeg 옵션에 `-segment_format_options movflags=+faststart`가 있었다. faststart는 파일을 닫을 때 재생 정보(moov)를 파일 앞으로 옮기려고 **파일 전체를 다시 쓴다.** 100MB를 읽고 다시 쓰면 5~10초가 걸린다.

**근본 원인**
- faststart 작업 동안 ffmpeg가 표준 입력을 읽지 않는다 → Picamera2 H.264 인코더가 ffmpeg에 쓰다가 막힌다 → 인코더가 카메라 프레임 버퍼를 돌려주지 못한다 → 버퍼(4개)가 바닥나 **실시간 캡처까지 멈춘다** → 감시 기능이 5초 기준으로 "멈춤" 판정.
- 감시 기능을 넣기 전에도 10분마다 화면이 몇 초씩 멈췄지만, 저절로 풀려서 눈에 띄지 않았다.

**해결**
- 녹화 옵션에서 faststart를 뺐다 (`recorder.segment_args`). 파일을 닫을 때는 moov를 끝에 붙이기만 해서 즉시 끝난다.
- moov가 파일 끝에 있어도 브라우저는 HTTP Range 요청으로 끝부분을 먼저 읽어 재생한다. Flask `send_file(conditional=True)`가 Range를 지원한다.
- 확인: 10분 경계 전후 1분 동안 프레임이 끊긴 최대 시간 0.09초, 멈춤 판정 없음. 녹화 파일은 `ftyp, free, mdat, moov` 구조로 정상 재생, 아이폰에서도 재생 확인.

**재발 방지**
- 녹화에 faststart를 다시 넣지 않는다 (CLAUDE.md "다시 하면 안 되는 것").
- 대기열(버퍼)을 넣어 막힘을 흡수하는 방법은 쓰지 않는다. Pi 녹화 ffmpeg는 `-use_wallclock_as_timestamps`로 받은 시각을 프레임 시간으로 쓰기 때문에, 몰아서 넘기면 그 구간이 빨리감기처럼 기록된다.
- 멈춤 기록이 정각 근처에 몰리면 녹화 쪽 막힘을 먼저 의심한다.

## 2. Pi 카메라 화면이 몇 시간 동안 같은 장면으로 멈춰 있음

**증상**
- 웹에서 Pi 카메라가 전날 저녁 화면으로 멈춰 있었다. 같은 시각부터 Pi 녹화도 12시간 40분 동안 비어 있었다. Tapo는 정상이었다. 예전에도 가끔 있었고 재부팅으로만 복구했다.

**진단 과정**
1. 마지막 Pi 녹화 파일의 수정 시각이 멈춘 시각(21:41)과 같았다 → 화면만이 아니라 카메라 자체가 프레임을 안 보냄.
2. 그 시각 서비스 로그에 libcamera 오류:
   ```
   Dequeue timer of 1000000.00us has expired!
   Camera frontend has timed out!
   Please check that your camera sensor connector is attached securely.
   ```
3. journal 전체에서 같은 오류를 찾으니 4월부터 13번(1~4주에 한 번). 13번 중 10번은 직전 2분 동안 서보를 움직인 적이 없었다. 매번 재부팅으로 복구했다.
4. 멈춘 상태에서 **재부팅 없이 서비스만 재시작**하니 카메라가 바로 살아났다 → 카메라를 닫았다 다시 열면 복구 가능.

**근본 원인**
- 센서가 CSI로 프레임을 보내지 않는 하드웨어 문제가 가끔 생긴다. libcamera는 이 상태에서 스스로 복구하지 않는다.
- 코드가 `capture_array()`를 **시간 제한 없이** 기다려서, 프레임이 안 오면 영원히 기다렸다. 녹화와 움직임 감지도 같은 카메라라 함께 멈췄고, 알아챌 장치가 없었다.
- 센서가 멈추는 하드웨어 원인은 확정하지 못했다. 리본 케이블을 새것으로 바꿔도 생긴다. 남은 의심은 서보 전원: 서보 보드 VCC가 Pi 5V에 연결돼 있어, 서보 전류가 Pi와 같은 5V를 쓴다 (서보 사양 3.6~4.8V보다 약간 높음).

**해결** (`picam.VideoGet`)
- `capture_array(wait=False)` + `wait(job, timeout=5)`로 바꿔 **5초 안에 프레임이 안 오면 감지**.
- 감지하면 녹화를 잠깐 멈추고(`before_restart`) → 카메라 `stop`/`close` → 새로 열기 → 녹화 재개(`after_restart`).
- 시험하다 보니 **`picam2.stop()`과 `stop_encoder()` 자체가 영원히 끝나지 않는 경우**가 있었다. 그래서 다시 열기 전체를 `run_with_timeout(…, 30)`으로 감싸고, 시간 안에 안 끝나거나 3번 실패하면 녹화를 닫고 `os._exit(1)` → systemd가 서비스를 새로 띄운다. 녹화 닫기도 20초까지만 기다린다.
- 멈춤/복구는 `logs/camera_events.log`에 남기고, 웹 상단 배너로 알린다.
- 확인 범위: "프레임이 안 오는 상황"을 흉내 낸 시험(다시 열기로 7.4초 만에 복구, 다시 열기 실패 시 27초 만에 서비스 재시작 요청, 닫기 멈춤 시 시간 제한 후 재시작 요청)은 통과했다. 진짜 센서 멈춤(`Camera frontend has timed out`)은 이 기능을 넣은 뒤 아직 생기지 않아서, 실제 상황에서 다시 열기로 복구되는지는 미확인이다. 운영 중 기록된 멈춤은 대부분 1번 항목의 가짜 멈춤이었다.

**재발 방지**
- 카메라 프레임은 반드시 시간 제한을 두고 기다린다.
- 카메라를 닫는 동작도 멈출 수 있다고 가정하고 시간 제한을 둔다.
- 하드웨어 원인을 줄이려면 서보 전원을 별도 5V로 분리(GND만 공통)하는 방법이 남아 있다.

## 3. 팬틸트가 특정 각도에서 계속 덜덜 떨림

**증상**
- 바닥에 단단히 고정한 뒤, 좌우로 움직이면 도착한 뒤에도 계속 덜덜 떨렸다. 위아래는 괜찮았다.

**진단 과정**
1. (1차, 실패) "이동 후에도 PWM 신호를 계속 보내서 서보가 위치를 붙잡느라 떨린다"고 보고, 팬 서보만 이동 0.5초 뒤 신호를 끄게 했다. 그래도 떨렸다.
2. 화면 떨림을 숫자로 재는 방법을 만들었다: 연속 프레임 사이 이동량을 위상 상관(`cv2.phaseCorrelate`)으로 계산.
3. 측정해보니 **신호를 꺼도 떨렸고** 오히려 더 자주 떨렸다 (신호 끔 6번 중 5번, 유지 3번 중 1번). 이 디지털 서보는 신호가 끊겨도 마지막 위치를 붙잡는다. 신호 끄기는 되돌렸다.
4. 각도를 0~90°로 훑어보니 **특정 위치(20° 근처)에서만** 떨렸다. 펄스 값을 1 tick씩 바꿔봐도 그 구간 전체가 떨렸다.
5. (2차) 사용자가 재현한 19°→29° 이동을 서비스로 그대로 해보니, 29°에 도착한 뒤 0.5초마다 5~16px씩 **8초 넘게 계속** 흔들렸다. 19°로 돌아오면 1초 안에 멈췄다.
6. 29° 도착 후 2~6초 흔들림을 방식별로 비교 (두 번씩):

   | 도착 방식 | 흔들림 |
   |---|---|
   | 한 번에 이동 (기존) | 173.5px, 115.0px |
   | 0.6초에 걸쳐 부드럽게 | 12.2px, 10.3px |
   | 반대쪽(39°)에서 한 번에 | 310.8px, 111.5px |
   | PWM 주기 100Hz | 24.0px, 180.8px |
   | 참고: 19°에 가만히 | 7.6px, 6.0px |

**근본 원인**
- 서보가 목표 펄스를 한 번에 받으면 최고 속도로 달려가 급정지한다. 특정 각도는 서보가 위치를 잡기 불안정한 구간(데드밴드 3μs로 매우 좁음, 하중)이라, 그 충격으로 **헌팅(목표 근처에서 왔다 갔다 하는 떨림)** 이 시작된다.
- 바닥에 그냥 놓았을 때는 받침대가 살짝 밀리며 충격을 흡수했지만, 단단히 고정하자 충격이 흡수되지 않아 떨림이 계속 이어졌다.
- 팬 서보는 틸트 서보·브래킷·카메라를 통째로 돌려 관성이 커서 더 심했다.

**해결** (`pan_tilt.PanTiltServo`)
- 펄스를 20ms마다 조금씩, 코사인 곡선으로 천천히 출발·천천히 멈추게 보낸다. 이동 시간은 거리에 따라 0.3~1.0초.
- 버튼은 목표 각도만 바꾸고 바로 응답하며, 백그라운드 스레드가 두 축을 움직인다.
- 확인: 1°~20°, 연타까지 웹 버튼으로 시험해서 도착 후 흔들림 9~16px (가만히 있을 때 수준). 19°→29°도 16px.

**재발 방지**
- 서보를 목표로 한 번에 보내지 않는다. PWM 신호 끄기는 효과가 없다는 것도 기록해 둔다 (CLAUDE.md).
- 외부 충격(문 닫힘 등)으로 시작된 떨림은 막지 못한다. 받침대 아래 고무 패드를 권장.
- 덤으로 알게 된 것: 코드의 각도 0~90은 실제 150° 이상 회전에 대응한다 (명령 10° ≈ 실제 17°, 화각 62°에서 화면 이동량으로 계산).

## 4. 서보가 떨리면 움직임 감지가 움직임으로 기록함

**증상**
- 카메라를 움직이지 않았는데 서보가 혼자 살짝 떨릴 때 Pi 카메라 녹화 목록에 움직임 표시가 생겼다.

**진단 과정**
- 감지 방식: 320x180 흑백 프레임을 0.33초 전 프레임과 비교해, 밝기 차이 25 넘는 픽셀이 0.5~60%면 움직임.
- 카메라가 몇 픽셀만 흔들려도 화면 속 모든 경계선이 어긋나 바뀐 픽셀이 1~10% 나온다. 고양이가 지나갈 때와 숫자가 비슷해서 구분이 안 됐다.
- 카메라를 버튼으로 돌린 직후 4초는 감지를 쉬지만, 혼자 떨리는 건 프로그램이 알 수 없다.

**근본 원인**
- 프레임 차이 방식은 "화면 전체가 같이 밀린 것(카메라 흔들림)"과 "일부만 바뀐 것(물체 움직임)"을 구분하지 못한다.

**해결** (`motion.shake_compensated_ratio`)
- 두 프레임 사이 화면 전체가 얼마나 밀렸는지 위상 상관으로 먼저 계산하고, 그만큼 되돌려 맞춘 뒤 비교한다.
- 처음에는 8px 이상 흔들림이 덜 보정됐다 → 화면 가장자리가 계산을 방해해서 Hanning 창을 적용하니 정확해졌다.
- 추가로 최근 3번 중 2번 이상 움직임이어야 기록한다 (한 번 튀는 건 무시).
- 시험 (실제 프레임을 1~20px 밀어서 흉내): 예전 방식은 모두 "움직임", 새 방식은 모두 "없음". 고양이 크기 물체를 움직이면 흔들림이 같이 있어도 "움직임". 비교 1번에 약 9ms, 초당 3번이라 CPU 약 2.8%.

**재발 방지**
- 근본적으로는 서보 떨림 자체를 줄이는 게 맞다 (3번 항목).

## 5. Tapo 움직임 알림이 몇 시간 뒤 조용히 끊김

**증상**
- Tapo 카메라 자체 움직임 감지(ONVIF 이벤트)를 받아 기록했는데, 첫날 이후 Tapo 움직임 기록이 하나도 없었다. 오류 로그도 없었다.

**진단 과정**
1. 서비스를 재시작한 직후에는 기록이 생겼다 → 시간이 지나면 끊기는 문제.
2. 직접 구독해보니 카메라는 정상으로 알림을 보냈다 (움직임이 있을 때 1분에 수백 개).
3. onvif-zeep 소스(`ONVIFCamera.update_xaddrs`)를 읽어보니, **`ONVIFCamera()`를 만들 때마다 만료 시간 없는 PullPoint 구독을 몰래 하나 만들고**, `create_pullpoint_service()`는 내가 만든 구독이 아니라 그 숨은 구독에 연결됐다.
4. 코드는 4분마다 `ONVIFCamera()`를 새로 만들고 있었다 → 사라지지 않는 구독이 하루 360개씩 쌓였다.
5. 라이브러리는 구독 생성 실패를 `except: pass`로 삼켜서 오류가 안 보였다.

**근본 원인**
- Tapo가 받을 수 있는 구독 수를 넘자 새 구독에 알림을 보내지 않았고, 라이브러리가 그 실패를 숨겼다.

**해결**
- `tapo.connect_onvif()`: 연결 직후 라이브러리의 숨은 구독을 `Unsubscribe`로 해지한다 (`subscription_manager`로 SubscriptionManagerBinding 클라이언트를 직접 만듦). PTZ 연결도 이걸 쓴다.
- 구독 하나를 1분마다 `Renew`하는 방식으로도 고쳤지만, 최종적으로는 **Tapo 움직임 감지도 Pi와 같은 화면 비교 방식으로 바꿨다.** 이미 실시간 화면용으로 받는 프레임을 쓰므로 부담은 CPU 약 3%이고, 카메라 펌웨어·앱 설정에 휘둘리지 않는다.
- Tapo 영상 왼쪽 위 시각 표시는 감지에 영향 없음을 확인 (변화량 최대 0.014%, 기준 0.5%).

**재발 방지**
- `ONVIFCamera()`를 직접 만들지 말고 `connect_onvif()`를 쓴다 (CLAUDE.md).
- 진단하면서 만든 구독이 카메라에 남아 있을 수 있으므로, 이상하면 Tapo 카메라를 한 번 재부팅한다.

## 6. 서비스를 재시작하면 녹화 중이던 파일이 깨짐

**증상**
- 서비스를 재시작하면 녹화 중이던 10분 파일이 `moov atom not found`로 재생되지 않았다.

**진단 과정**
1. 처음에는 ffmpeg를 `prctl.set_pdeathsig(SIGKILL)`로 앱과 같이 죽게 해뒀다 → SIGKILL은 파일을 닫을 틈을 주지 않는다. SIGTERM으로 바꿨다.
2. 그래도 깨졌다. `systemctl restart`가 0.16초 만에 끝났고, 로그에 ffmpeg의 `Received > 3 system signals, hard exiting`이 있었다.
3. systemd 기본 `KillMode=control-group`은 앱과 ffmpeg **모두에게 동시에** SIGTERM을 보낸다. 여기에 pdeathsig까지 겹쳐 ffmpeg가 신호를 여러 번 받았다. ffmpeg는 종료 신호를 3번 넘게 받으면 파일 정리를 포기한다.

**근본 원인**
- MP4는 녹화를 끝낼 때 moov(목차)를 써야 재생된다. 종료 신호가 겹쳐서 ffmpeg가 moov를 못 쓰고 꺼졌다.

**해결**
- systemd unit에 `KillMode=mixed`, `TimeoutStopSec=60` (0번 항목, git에 없음): SIGTERM은 앱에만 보낸다.
- 앱이 SIGTERM을 받으면 `recorder.stop_all()`로 Tapo ffmpeg에는 SIGINT를 **한 번만** 보내고, Pi 녹화는 인코더를 멈춰 ffmpeg 입력을 닫는다. 파일이 닫힐 때까지 기다린 뒤 종료.
- 정전처럼 갑자기 꺼져 깨진 파일은 moov 유무를 검사해 녹화 목록에서 숨긴다 (`recorder._is_playable`).
- 확인: 재시작 직전까지 녹화 중이던 34초짜리 파일이 영상·소리 모두 정상.

**재발 방지**
- ffmpeg를 SIGKILL로 죽이지 않고, 종료 신호는 한 번만 보낸다.
- 정전 시에는 녹화 중이던 최대 10분을 잃을 수 있다는 한계가 있다.

## 7. USB 마이크를 WebRTC로 열 수 없음

**증상**
- aiortc의 `MediaPlayer("hw:3,0", format="alsa")`로 USB 마이크를 열면 `Unknown PCM hw:3,0` / `Cannot access file /tmp/vendor/share/alsa/alsa.conf`.

**진단 과정**
1. `ALSA_CONFIG_PATH`를 시스템 경로로 지정 → 이번엔 `/tmp/vendor/lib/alsa-lib/libasound_module_conf_pulse.so`를 못 찾음.
2. `format="pulse"` → `no container format 'pulse'`.
3. `av.formats_available`를 확인하니 pip로 설치한 PyAV(aiortc 의존성)에는 `alsa`, `oss`뿐이고, 그 ALSA는 빌드 서버 경로(`/tmp/vendor`)를 바라보는 번들 라이브러리였다.

**근본 원인**
- pip 휠에 들어 있는 PyAV는 자체 ALSA를 번들로 갖고 있어 라즈베리파이 시스템 ALSA 설정과 장치를 쓰지 못한다.

**해결**
- 마이크 캡처는 시스템 PortAudio를 쓰는 `sounddevice`로 하고, 받은 PCM을 aiortc `AudioStreamTrack` 하위 클래스(`MicrophoneTrack`)로 WebRTC에 넘긴다.
- `sounddevice`는 `libportaudio2`(apt)가 필요하다 (0번 항목).

**재발 방지**
- 장치 이름 대신 `sounddevice.query_devices()`의 번호를 쓴다 (`app.AUDIO_DEVICE`).

## 8. 새로고침 후 소리 버튼을 누르면 "Device unavailable"

**증상**
- 처음엔 소리가 나오는데, 페이지를 새로고침하고 다시 누르면 `PortAudioError: Device unavailable [-9985]`.

**근본 원인**
- 연결마다 마이크를 새로 열고 있었다. 새로고침하면 이전 연결이 서버에서 정리되기 전에 새 연결이 같은 마이크를 열려고 했다. 마이크는 한 번에 한 곳만 열 수 있다.
- 이전 연결을 닫고 잠깐 기다리는 방식은 첫 클릭에 소리가 안 나는 문제가 남았다.

**해결**
- 마이크는 **서버 시작 시 한 번만** 열고 계속 유지한다. 콜백에서 받은 소리를 `AudioFanout`으로 듣고 있는 모든 연결(그리고 Pi 녹화)에 나눠 준다. 연결은 구독만 붙였다 뗀다.

**재발 방지**
- 장치를 여는 쪽은 하나로 두고, 나눠 주는 구조를 유지한다. Pi 녹화 소리도 같은 방식으로 받는다.

## 9. 소리 연결은 되는데 아무 소리도 안 들림

**증상**
- 소리 버튼이 "켜짐"으로 바뀌는데 소리가 없었다.

**근본 원인**
- 서버가 SDP answer를 만들자마자 응답해서, ICE 후보(연결 경로 정보)가 아직 다 모이지 않은 answer가 브라우저로 갔다. trickle ICE를 구현하지 않았으므로 브라우저는 연결 경로를 알 수 없었다.

**해결**
- answer를 만든 뒤 `iceGatheringState == "complete"`가 될 때까지 기다렸다가 응답한다 (`app.offer`). 버튼 응답이 조금 늦어지는 대신 한 번에 연결된다.

## 10. 아이폰에서만 소리가 안 나옴

**증상**
- 맥북 크롬·사파리는 되는데 아이폰(크롬도 내부는 WebKit)은 안 됐다. 고치다 보니 한때는 맥북까지 안 나왔고, 다음엔 아이폰에서 버튼을 두 번 눌러야 나왔다.

**진단 과정**
1. iOS는 오디오 재생을 **사용자 제스처(탭) 안에서** 시작해야 허용한다. `ontrack`은 네트워크 연결 뒤에 비동기로 와서 제스처로 인정받지 못했다.
2. AudioContext + `createMediaStreamSource`로 바꿨다가 맥북까지 소리가 안 났다. 연결을 기다리는 몇 초 동안 브라우저가 AudioContext를 자동으로 멈추기 때문으로 보였고, 이 방식은 버렸다.
3. 버튼을 누른 순간 0샘플 무음 WAV를 `await audio.play()`로 재생 → 맥북과 아이폰 모두 되지만 아이폰은 두 번 눌러야 했다. 0초짜리라 바로 끝나서 "재생 중" 상태가 유지되지 않았다.

**해결** (`templates/get_cam.html` `toggleAudio`)
- 버튼을 누른 순간(await 없이) 무음 WAV를 `loop = true`로 재생해서 `<audio>` 요소를 "재생 중" 상태로 둔다. 연결되면 `srcObject`를 실제 스트림으로 바꾼다.
- `<audio>`에는 `autoplay playsinline`.

**재발 방지**
- iOS에서 미디어·공유 창(`navigator.share`)은 버튼을 누른 그 순간, 비동기 작업 전에 시작해야 한다. 화면 저장도 같은 이유로 캔버스에서 동기적으로 파일을 만든다.

## 11. 크롬이 로그인할 때마다 "안전하지 않은 정보" 경고

**증상**
- 로그인할 때마다 크롬이 "안전하지 않은 정보를 제출하려 함" 창을 띄웠다.

**근본 원인**
- 웹이 HTTP(`http://<Tailscale IP>:5000`)로 열려 있었다. Tailscale(WireGuard)이 전 구간을 암호화하지만 브라우저는 그 사실을 알 수 없어서 HTTP 폼 제출을 경고했다.

**해결**
- `tailscale serve`로 Tailscale 인증서(Let's Encrypt) HTTPS를 붙이고, Flask는 `127.0.0.1`에서만 듣게 바꿨다 (0번 항목). 예전 HTTP 주소와 집 Wi-Fi 주소로는 접속이 막힌다.
- 덤: 나중에 폰 마이크로 말하는 기능을 만들려면 HTTPS가 필수다 (브라우저는 HTTPS에서만 마이크 허용).

**재발 방지**
- 서버를 `0.0.0.0`으로 열지 않는다. 버튼용 API에도 로그인 확인(`api_login_required`)을 붙였다.

## 12. Pi 카메라 화각이 사양보다 좁음

**증상**
- Camera Module v2(IMX219) 사양은 가로 62°인데 실제로는 훨씬 좁았다.

**진단 과정**
- 서비스 로그의 `Selected sensor format: 1920x1080`. IMX219의 1920x1080 모드는 센서(3280x2464) **가운데만 잘라 읽는** 모드다.
- `capture_metadata()["ScalerCrop"]`로 확인: 사용 영역 1920x1080 → 가로 39°, 세로 22.5°.

**근본 원인**
- 출력 크기(1280x720)만 정하면 libcamera가 비율이 같은(16:9) 센서 모드를 자동으로 고르는데, 그 모드가 크롭 모드였다.

**해결**
- 센서 모드를 1640x1232(센서 전체를 2x2로 묶어 읽는 모드)로 지정 (`picam.SENSOR_MODE`). 사용 영역 3280x1844(위아래만 잘림) → 가로 62.3°, 세로 37.5°, 비율 16:9 유지, 34fps 동일.

## 13. Tapo 녹화를 MP4로 저장하면 바로 실패

**증상**
- `ffmpeg -i rtsp://… -c copy out.mp4` → `Could not find tag for codec pcm_alaw in stream #1`.

**근본 원인**
- Tapo RTSP 소리는 G.711 A-law(8kHz)인데 MP4 컨테이너가 이 코덱을 지원하지 않는다.

**해결**
- 영상은 그대로 복사(`-c:v copy`, 재인코딩 없음 → CPU 약 3%), 소리만 AAC로 변환(`-c:a aac -b:a 32k`).

## 14. 아이폰에서 버튼을 빠르게 누르면 화면이 확대됨

**증상**
- 방향 버튼을 빠르게 연속으로 누르면 iOS가 더블탭으로 인식해 화면 전체를 확대했다.

**해결**
- 버튼과 페이지에 CSS `touch-action: manipulation` (더블탭 확대만 끄고 핀치 확대는 유지).
- 영상 확대는 브라우저 확대 대신 직접 구현(더블탭 2배, 두 손가락 1~4배, 끌어서 이동). 영상 위에서는 `touch-action: pan-x pan-y`, 확대 중에는 `none`으로 브라우저 확대·스크롤과 겹치지 않게 했다. 자세한 동작은 `docs/app.md`.

## 15. Tapo 연결이 하루 수백 번 끊기고, 오류 기록에 이유가 없음

**증상**
- 하루 만에 Tapo 관련 경고가 수십~수백 건 쌓였다 (48시간 275건). 오류 목록에는 "Tapo 영상 연결이 끊김", "Tapo 녹화(ffmpeg)가 끝남 (종료 코드 0/1)"만 있고 이유가 없었다.

**진단 과정**
1. 오류 기록 종류: 실시간 영상 끊김 94건, 녹화 ffmpeg 종료 코드 0 106건, 코드 1 75건.
2. ffmpeg의 자세한 메시지는 서비스 로그(journal)에만 있었다: `Connection timed out` 236건, `No route to host` 몇 건 → 라즈베리파이가 카메라 RTSP 포트에 연결 자체를 못 함.
3. 라즈베리파이 Wi-Fi는 신호 -32dBm(5GHz), 48시간 동안 끊김 기록 없음 → 라즈베리파이 쪽은 정상.
4. 날짜별 끊김: 11/12 2건, **11/14 865건**, 11/17 3건, 11/19 7건, 11/20 36건, **11/21 232건** → 날마다 크게 들쭉날쭉.
5. 30분 동안 1초마다 ping과 RTSP 포트 연결을 확인: 카메라가 **몇 분마다 약 40초씩 네트워크에서 통째로 사라짐** (43초, 44초, …). "응답은 있는데 RTSP 거부"(재부팅 특징)는 한 번도 없었다.
6. 사용자 확인: 그즈음 **카메라 위치를 옮겼다**.

**근본 원인**
- 카메라를 옮긴 뒤 Tapo C210(2.4GHz만 지원)의 Wi-Fi 신호가 약해져, Wi-Fi 연결이 자주 끊겼다 다시 붙는다. 카메라 재부팅이나 코드 문제는 아니다.
- 기록이 많았던 이유: 한 번 끊길 때마다 실시간 영상과 녹화가 각자 3~5초마다 재시도하면서 매번 경고를 남겼다 (끊김 1번에 3건 이상).
- 기록에 이유가 없던 이유: OpenCV는 끊긴 이유를 알려주지 않고, ffmpeg 오류는 서비스 로그로만 나갔다.

**함께 발견한 문제: 비밀번호 노출**
- ffmpeg는 오류 메시지에 RTSP 주소를 그대로 찍는데, 주소에 **카메라 계정 아이디와 비밀번호**가 들어 있다 (`rtsp://<아이디>:<비밀번호>@…`). 서비스 로그(journal)에 24시간 동안 195줄이 쌓여 있었다.
- 진단 중 서비스 로그를 출력하면서 이 값이 작업 기록에도 노출됐다 ("password" 단어만 거르고 있었음). 카메라 계정 비밀번호 변경을 권장했다.

**해결**
- **비밀번호 가리기 (두 겹)**
  - Tapo 녹화 ffmpeg의 오류 출력(stderr)을 앱이 직접 받아서 계정 부분을 `rtsp://***@`로 바꾼다. 서비스 로그로 바로 나가지 않는다.
  - 모든 로그 출력(콘솔, 파일, JSON)에 같은 가리기를 적용한다 (`applog.redact`). 비밀번호에 `@`가 있어도 주소의 마지막 `@`까지 가린다.
- **끊긴 이유 구분**: 끊긴 순간 카메라 RTSP 포트에 직접 연결해서 이유를 붙인다 (`tapo.probe_rtsp`).
  - 응답 없음 → "카메라가 네트워크에서 응답하지 않음 (Wi-Fi 끊김 의심)"
  - 연결 거부 → "카메라가 연결을 거부함 (재부팅 중일 수 있음)"
  - 연결됨 → "카메라는 응답하지만 영상이 끊김"
- **기록 묶기**
  - 실시간 영상: 끊긴 순간 경고 1건(이유 포함), 다시 연결되면 일반 기록 1건(끊긴 시간 포함).
  - 녹화: 끊긴 순간 한 줄(이유 + 가린 ffmpeg 메시지). 카메라가 네트워크에서 사라진 경우는 실시간 영상 쪽 경고와 겹쳐서 일반 기록으로만, 카메라는 살아 있는데 녹화만 실패하면 경고. 재시도는 기록하지 않고, 녹화가 15초 넘게 이어지면 "다시 시작됨 (N초 끊김, 재시도 M번)" 한 줄.
- 시험: 연결 안 되는 가짜 주소(가짜 계정 포함)로 시작했다가 진짜 주소로 바꿔서, 끊김 1줄 → 복구 1줄("38초 끊김, 재시도 1번"), 로그 어디에도 진짜·가짜 비밀번호가 없음을 확인.

**결과 (공유기 설정 변경 후)**
- 2026-11-23 22시경 공유기 2.4GHz를 **채널 자동 → 1, 대역폭 40MHz → 20MHz**로 바꿨다. 주변 공유기를 확인해 보니 강한 이웃이 10번에 있었고, 40MHz는 2.4GHz 대역 대부분을 차지해 이웃과 겹친다. 바꾼 직후 6시간 정도는 계속 끊겼다 (시간당 1~6번).
- 2026-11-24 04:53에 공유기 Wi-Fi가 한 번 다시 시작됐다 (라즈베리파이 NetworkManager 기록에 "ssid-not-found" 약 40초). 그 순간부터 끊김이 멈췄다.
- 그 뒤 4일(11/24 05시 ~ 11/28 12시) 동안 끊김 **1번**(11/24 11:03, 약 20초). Tapo 녹화 파일 433개(3일치)가 빈 곳 없이 10분 간격으로 이어졌고, 카메라 ping 손실 0%.
- 같은 날 라즈베리파이를 고정 IP에서 DHCP로 바꿨지만(16:36), 끊김이 멈춘 뒤라 원인이 아니다. 카메라 위치 등 다른 변경은 없었다.
- 채널 변경과 공유기 재시작 중 무엇이 결정적이었는지는 구분하지 못했다. 설정이 재시작 뒤에야 완전히 적용됐을 가능성이 있다.

**재발 방지**
- 서비스 로그(journal)를 읽거나 출력할 때는 `sed -E 's#rtsp://[^/ ]*@#rtsp://***@#g'`로 계정을 가린다 (CLAUDE.md).
- 외부 프로그램의 출력을 서비스 로그로 그대로 흘려보내지 않는다. 비밀값이 섞일 수 있다.
- Wi-Fi: 카메라를 공유기 가까이 두거나 장애물을 피하고, 필요하면 중계기/메시 노드를 둔다. 2.4GHz는 채널을 1, 6, 11 중 덜 붐비는 곳으로, 대역폭은 20MHz로 정한다 (공유기 "채널 추천"이 1/6/11이 아닌 채널을 고를 수 있음). 설정을 바꾼 뒤 효과가 없으면 공유기를 한 번 재시작해 본다. 위치를 바꾼 뒤에는 같은 방식(1초 간격 ping + RTSP 포트 확인)으로 전후를 비교한다.

## 16. 실시간 영상이 집 Wi-Fi에서도 버벅임

**증상**
- 공유기 2.4GHz 설정을 바꾼 뒤 웹 화면이 매끄럽지 않다고 느꼈다. 아이폰과 맥북 모두 5GHz에 연결돼 있었다.

**진단 과정**
1. 라즈베리파이 Wi-Fi: 5GHz, 신호 -30dBm, 433Mbps, 공유기까지 ping 평균 2ms, 손실 0% → 정상. 2.4GHz 설정과도 무관.
2. 라즈베리파이 → 맥북 ping 4~14ms (정상), → 아이폰 평균 81ms, 최대 874ms (아이폰 Wi-Fi 절전으로 흔한 모습).
3. 서버가 보내는 영상: 두 카메라 모두 20fps, 0.5초 넘는 멈춤 없음 → 서버 쪽은 고르게 보냄.
4. **영상 용량: Pi 52Mbps, Tapo 30Mbps.** OpenCV 기본 JPEG 품질(95)로 Pi 한 장이 약 316KB였다. Tailscale 암호화에도 CPU 약 35%를 썼다.

**근본 원인**
- MJPEG는 매 장면을 사진 한 장으로 보내서 영상통화(1~3Mbps)의 20배쯤 무겁다. 버퍼 없이 바로 보여주는 방식이라, Wi-Fi 속도가 잠깐만 떨어져도(아이폰 절전 지연 등) 화면이 멈춘다.

**해결**
- 실시간 영상을 **WebRTC + H.264**로 바꿨다. 카메라 쪽에서 이미 압축된 H.264를 다시 압축하지 않고 그대로 보낸다 (`docs/webrtc_video.md`). Pi 약 1.5Mbps, Tapo 약 0.2Mbps. MJPEG는 예비 경로로 남겼다.
- (당장 쓸 수 있는 대안으로 JPEG 품질 80도 측정했다: Pi 127KB/장(21Mbps), Tapo 88KB/장(14Mbps). 근본 해결이 아니라 쓰지 않았다.)

**바꾸면서 겪은 문제**
1. **영상이 안 나옴 (VP8 선택)**: 서버가 H.264 대신 VP8로 답했다. aiortc는 브라우저 offer를 적용하는 순간 코덱을 정하는데, H.264 고정을 그 뒤에 해서 효과가 없었다. 트랙 추가와 코덱 고정을 `setRemoteDescription` 앞으로 옮겨 해결.
2. **연결마다 5초 지연**: `/offer` 응답이 항상 5.0초. 서버가 구글 STUN 서버로 공인 주소(srflx 후보)를 알아내느라 기다렸다. 접속은 항상 Tailscale 안이라 필요 없어서 `iceServers=[]`로 끔 → 0.1초. 기존 소리 버튼도 같이 빨라졌다.
3. **첫 화면 3초 넘게 걸림**: 새 연결은 키프레임부터 볼 수 있는데 Pi 인코더 키프레임 간격이 약 3.6초였다. 30프레임(약 1.8초)으로 줄여 첫 화면 0.1~1.5초.
4. **가끔 검은 화면**: 서버 로그에서 연결이 대부분 "Consent to send expired"(브라우저가 말없이 사라짐: 앱 전환, 화면 꺼짐, 짧은 Wi-Fi 끊김)로 끝났다. 페이지가 그때마다 `<video>`를 바로 비우고 다시 연결해서 검게 보였고, 저절로 돌아오는 `disconnected`도 즉시 끊었다. 다시 연결하는 동안 마지막 화면을 유지하고 새 영상 데이터가 들어올 때(`unmute`) 바꿔 끼우게 했다. `disconnected`는 5초 기다린다. 고친 뒤 사용자 확인에서 재연결·실패 없음.

**재발 방지**
- aiortc에서 코덱을 정할 때는 `setRemoteDescription` **전에** `setCodecPreferences`를 한다 (CLAUDE.md).
- 서버 쪽 WebRTC에 STUN을 다시 넣지 않는다 (Tailscale 안에서는 필요 없고 연결마다 5초 지연).
- 실시간 영상 연결의 시작(이유 포함)과 끝(상태, 유지 시간)을 `logs/app.log`에 `webrtc` 이름으로 남긴다. 화면이 끊기면 이 기록부터 본다.
